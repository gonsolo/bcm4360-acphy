# Status 2026-09-27 (early morning, continuing from 09-26)

## Since the last status note

- **5 GHz receive works** (`b30ff88`): the decoded first-load state must be
  applied in *last-write order*, not address order. wl also writes through
  broadcast aliases (PHY address | 0x1000, radio 0x6xx/0x7xx reach both
  cores), so naively replaying in address order let stale broadcast writes
  clobber later per-core values (RF control overrides 0x725..0x73a,
  0x645/0x845, radio 0x049/0x249). With the fix: `ac_5ghz=1 ac_5g_80=1` on
  channel 112, CRS glitches ~970/s -> 0, 88/100 router beacons decoded.
  5 GHz transmit is unexplored and unverified (`wip-5ghz-tx` branch); do not
  combine 5 GHz + 80 MHz + TX injection without the user present — see the
  freeze note below.

- **Hard freeze, 2026-09-26 ~23:55**: two Claude sessions were driving the
  chip concurrently. The one that kept going loaded `ac_5ghz=2 ac_5g_80=1`
  and injected frames three times in five minutes; the machine froze solid
  (mouse and window manager both dead, no kernel log at all — looks like a
  PCIe bus hang, which panic_on_oops can't catch). Rule: only one session
  may touch this hardware at a time; treat toggling `BCMA_IOCTL` PHY-BW bits
  on a running/associated core, especially combined with TX, as crash-prone
  and don't run it unattended.

- **Firmware-ACK failure reconfirmed with a cleaner, non-association test**
  (`tools/probeack.sh` + `tools/inject_probe.pl` + `tools/fc_retry.py`): an
  idle station (managed-mode interface up, no auth/assoc needed) sends
  directed probe requests; the AP's unicast probe responses are readable
  directly off b43's own monitor vif. Reading the real frame-control retry
  bit (0x0800) byte-by-byte — tcpdump's summary line doesn't print "Retry"
  for management frames, which had hidden this in `acktest.sh`'s original
  grep — shows **65-75% of probe responses are retries** (the AP's default
  retry count for this frame type), and the ucode's own counters confirm
  the same event count exactly: `txackfrm` (ACKs the firmware believes it
  sent) equals `txphyerr` (PHY transmission errors) almost 1:1. So this is
  the same failure as with full WPA2 association, just isolated with a much
  smaller reproduction: the firmware's automatically-generated ACKs never
  reach the air, while identically-rated host-generated frames (the probe
  requests themselves) go out and get received by the AP every time.

  One side curiosity, not yet explained and not obviously related: our own
  injected probe requests always appear twice in the capture, 1-2 ms apart,
  byte-identical (not a retry-bit retransmission — both copies decode with
  retry=0). Monitor-vif TX-feedback loopback quirk, or a genuine one-shot
  driver/firmware retry that doesn't set the retry bit? Unconfirmed.

## Ruled out for the ACK failure (adds to 09-26's list)

Nothing new ruled out this round; the probe-based test is a better
*instrument* for the same failure, not a new place to look. The failure is
specific to firmware-generated SIFS-timed responses (ACK, and by extension
probably beacon/probe-response transmission scheduling); host-generated
frames at the same rate, same PHY config, same antenna path are clean.

## Next idea (unchanged, still not attempted)

AP-beacon test: put b43 briefly into AP mode so the firmware transmits
beacons on its own schedule, without the 10 us SIFS deadline an ACK has.
Clean beacons would point at the fast RX->TX turnaround specifically, not
at how the response content/rate is configured. Needs hostapd and an open
test SSID visible to neighbours for a few minutes (user already agreed to
that in principle on 09-26, but ran out of session time before it was set
up); do this with the user present given tonight's freeze.

  no-association ACK test described above.

- `tools/ack_setup5g.sh`, `tools/txsb_sweep.sh` (branch `wip-5ghz-tx` only):
